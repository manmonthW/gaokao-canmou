# 智能匹配（Match）计算逻辑分析

> 分析对象：`webapp/backend/app/services/match.py`（普通类智能匹配 Phase 2 MVP）
> 关联脚本：`webapp/scripts/backtest_match.py`（回测诊断）
> 分析时间：2026-08-04
> 说明：本文仅为静态读码分析，用于评估现有匹配逻辑的方法论与局限，未改动任何代码。

---

## 一、核心方法：位次法（不是分数法）

整个匹配基于一个前提——**位次（省排名）是唯一跨年可比的锚点**，分数不可比（每年试题难度、控制线不同）。

- 考生位次记为 `R`。
- 与院校专业的历史「投档最低位次」`lowest_rank` 比较。
- 判定规则：`R <= 历史位次` 表示考生排名更靠前（等价分数更高），录取把握更大。

---

## 二、六步流程拆解

### 第一步 输入校验
- 只给分数不给位次时，调 `locate.score_to_rank` 反查位次。
- 落在区间时取 `rank_range[0]`（区间上界，更保守）。
- 位次拿不到或 `<= 0` 直接报错返回。

### 第二步 数据过滤（关键约束）
```sql
WHERE category = ? AND subject = ? AND batch = ?
  AND is_collection = FALSE        -- 只用常规批，排除征集
  AND score_kind = '投档最低分'      -- 只用投档，不用录取
```
设计要点：
- 科类 / 选科 / 批次**严格一致**才比较。
- 排除征集志愿（征集是补录，规律不同）。
- **只用「投档最低分」**，不用「录取最低分」——库里录取分仅 373 行，投档分有 3.7 万行。
  投档线代表「进档门槛」，不等于「录取门槛」（进档后仍可能被专业退档）。这是 MVP 妥协。

### 第三步 构造候选单元
- 单元键 = `(院校, 专业代码或专业名, 批次)`。
- **不按院校聚合**——同校不同专业位次差异巨大，聚合会掩盖专业级差异。

### 第四步 历史统计
每个单元跨 2025 / 2026 汇总：
- `best_rank` = 最小位次（最难年）
- `worst_rank` = 最大位次（最易年）
- `median_rank` = 中位位次
- `span` = 跨度（worst − best）
- `break_detected` 断档：`worst > median × 1.6`
- 辅助字段：`has_both_years`、`continuous`、`last_year_rank`

### 第五步 风险分类（核心算法，`_classify`）
判定顺序：
1. `n_years == 0`（无位次）→ **数据不足**
2. 高波动（`≥2 年` 且 `span/median ≥ 0.5` 且 `span ≥ 2000`）→ **高波动**
3. 否则按位次落点：
   - `R <= best` → **保**（优于历史最易年门槛）
   - `R <= median` → **稳**
   - `R <= worst` → **冲**
   - `R > worst` → **冲**（高风险冲刺）

### 第六步 排序
- 风险优先：保 > 稳 > 冲 > 高波动 > 数据不足。
- 同档内按 `rank_diff_last`（考生位次 − 去年位次）升序，最接近者靠前。

## 三、发现的问题（按严重度）

### 🔴 1. 两年数据下 median 无统计意义
只有 2025 + 2026 两个点时，`median([a,b]) = int((a+b)/2)`，且 `best = min`、`worst = max`。
- 「稳」档 = `min < R <= 平均`
- 「冲」档 = `平均 < R <= max`

两点求中位数在统计上没有代表性，分档边界完全由这两年偶然值决定。
回测脚本自己也注明「无法做严格滚动回测」。

### 🟠 2. 「保」档定义偏乐观
`R <= best`（历史最难那年的门槛）就判「保」。但 best 是历史最低位次，
未来若比历史更难就不保了。更稳健的做法是加安全边际（如 `R <= best × 0.9`）。
`backtest_match.py` 的 `margin_sensitivity` 正是为调这个 margin 准备的，
但**主服务 `_classify` 并未使用 margin**——回测调参结论没有回灌到生产逻辑。

### 🟠 3. 阈值全是默认猜测值，未经回测固化
`high_vol_rel=0.5`、`high_vol_abs=2000`、`break_multiplier=1.6` 注释都写着「待回测」。
`backtest_match.py` 存在但结论未落地——阈值仍是初始猜测。

### 🟡 4. 投档线 ≠ 录取线的系统性偏差
用投档最低分做门槛，会**系统性高估**录取把握（进档 ≠ 录取，
尤其是有专业级差 / 退档的院校）。用户看到的「保/稳/冲」实际是「能否进档」而非「能否被录取」。

### 🟡 5. `has_both_years` 与 `n_years` 口径不一致
- `has_both_years` 基于 `years`（含位次为空的年）
- `n_years` 基于 `ranks`（仅有位次的年）

一个单元可能 `has_both_years=True` 但 `n_years=1`（某年位次缺失），
分类会走「单年」分支，展示上可能让用户困惑。

### 🟡 6. 跨年可比性受批次改名影响
2026 本科提前批拆成 A/B 段后，同一单元在 2025（本科提前批）和 2026（A段/B段）的
`batch` 不同，`_build_unit_key` 含 batch，会被拆成两个单元，两年数据无法合并。
本科提前批的匹配在这次政策变化后跨年比对会失效。（这是数据现实，非代码 bug，但影响匹配质量。）

---

## 四、设计上做得好的地方

- 位次法而非分数法，方向正确。
- 单元不按校聚合，保留专业粒度。
- 排除征集、区分常规。
- 「数据不足」单独成档并显式告警，不硬套分类。
- 每个候选带 `risk_reason` 可解释文案。
- MVP 明确不输出「录取概率」（避免给出无依据的精确数字）。

---

## 五、总结

方法论（位次法、专业粒度、可解释、不编概率）是扎实的；但**分档算法在两年数据下统计基础薄弱**：
median 无意义、best 定义偏乐观、阈值未回测、投档 ≠ 录取的系统偏差。

本质是「用两年历史位次的区间落点做经验分档」，参考价值有，但精度和稳健性有限。

### 后续可选改进方向
1. 跑 `backtest_match.py`，用 2025→2026 的真实录取率校准分档边界与阈值，并把结论回灌 `MATCH_CONFIG` 与 `_classify`。
2. 「保」档引入安全边际 margin（如 `best × 0.9`），降低乐观偏差。
3. 补充「录取最低分」数据后，在 step4 叠加录取分细化「稳/保」判定，缓解投档 ≠ 录取偏差。
4. 统一 `has_both_years` 与 `n_years` 的年份口径，避免展示困惑。
5. 针对本科提前批 A/B 段的跨年断裂，考虑建立批次别名映射，使 2025 本科提前批可与 2026 A/B 段合并参考。
