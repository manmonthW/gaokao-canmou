## 0. 一页结论

**做什么**：在现有「定位 → 匹配 → 工作台」主线上加一个「AI 参谋助手」，让考生和家长用自然语言提问。
助手调用系统里已有的确定性能力（位次换算、冲稳保匹配、院校/专业详情、选科校验、趋势、方案体检）
查出事实，再用通俗语言解释、比较和给出下一步建议。

**不做什么**：AI 不自己判冲稳保、不输出录取概率、不补全缺失数据、不替用户生成正式志愿表、
不对艺术类和体育类给推荐。这些都是 PRODUCT.md 已定的边界，Agent 化以后仍然成立。

**怎么做**（沿用 PPT 项目验证过的混合架构）：

```
外层：LangGraph 确定性工作流（输入守卫 → 意图路由 → 子流程 → 校验 → 交付）
内层：局部范围的工具型 Agent（只读工具，最多 5 轮）
底层：现有 services（match / locate / schools / major_catalog / datacenter）+ 证据账本 + 校验器
模型：LangChain → EricAI OAuth → aigw → se-gpt-5.6-sol（后端直连，浏览器不接触凭证）
```

**关键设计**：网关的限制是**带工具的请求只能用 `reasoning_effort=none`**。所以把"查"和"想"拆成两个节点：
- 工具轮次关闭推理，只负责选工具、填参数；
- 综合节点不带工具，打开推理（low/medium），基于证据账本写结构化答案；
- 最后由确定性校验器核对答案里每个数字、每个院校专业是否都能在证据里找到。

**工期**：4 个阶段，单人约 7–8 周（不含下文 Gate 0 的前置修复和合规确认）。
按 2027 年 6 月下旬出分倒排，2027 年 4 月底前要完成压测和灰度。

**开工前必须先过 Gate 0**：合规和使用范围确认（见 §1.1），它可能决定整个功能能不能对公众开放。

## 1. 前置闸门（Gate 0）

### 1.1 合规与使用范围（阻断项，需要你确认）

| 问题 | 为什么重要 | 对设计的影响 |
|---|---|---|
| EricAI 网关（公司 Service Principal）是否允许用于**非公司业务**、服务**外部公众用户**？ | 目前复用的是 nir-report 的 SP 和 secret，调用量和费用都记在它名下；把外部考生的数据送进公司网关，可能违反内部使用条款 | 如果不允许，只能作为内部演示或邀请制内测；如果允许，要确认配额和费用归属，最好申请独立 SP |
| 面向境内公众提供生成式 AI 服务的监管要求（《生成式人工智能服务管理暂行办法》等）是否适用？ | 公开上线的 AI 问答功能通常要履行安全评估/备案；境外模型能否用于境内公众服务存在不确定性 | 架构层面**必须保持模型可替换**（LangChain 抽象，PPT 项目已同时支持 DeepSeek 和 EricAI），为以后切换到已备案的国内模型留路 |
| 用户数据出境与最小化 | 位次、选科、方案属于考生个人信息 | 只发送完成任务必需的字段（不发邮箱、用户名、IP）；日志设保留期 |

**建议的默认策略**（Gate 0 结论出来之前按这个做）：Agent 功能放在功能开关 `AGENT_ENABLED` 后面，
加登录白名单（邀请制内测），公开页面不暴露入口；模型提供方通过配置切换，业务代码不绑定 EricAI。

### 1.2 前置工程修复（来自上一轮评审的 P0，Agent 会放大这些问题）

| 项 | 为什么 Agent 依赖它 |
|---|---|
| **匹配缓存重构**：与位次无关的单元集合按「数据版本 + 类别/学科类/批次」缓存，分档和筛选每次现算；CPU 段放进线程池 | Agent 一次对话会用不同筛选调 2–4 次匹配。现在每次都是冷算，而且阻塞事件循环，Agent 的等待时间会直接翻倍 |
| **限流**（nginx `limit_req` + 应用层按用户/IP 计数） | LLM 调用有成本，匿名接口会被刷 |
| **compose 安全**：只读数据库角色、强 JWT_SECRET、收紧 CORS、删掉 `COPY data` | Agent 会读取 SQLite 用户库（任务表），镜像里不能带本地数据 |
| **后端容器改非 root，UID 10001** | EWS 上共享的 secret 是 `0400`、属主 10001；改 UID 后要 `chown` 用户数据卷 |
| **方案体检规则挪到后端**（目前只在 `usePlanner.analyzePlan`） | 阶段 2 的方案体检 Agent 需要在服务端调用同一套规则，规则只能有一份 |

## 2. 场景选择：哪些值得 Agent 化

用 PPT 项目文档里的「六问评分」（每项 1 分，4 分及以上才值得用工具型 Agent + 持久执行）：

| 场景 | 步骤不定 | 靠工具结果决策 | 跨数据源 | 较长/需人工 | 可验证 | 需隔离/并行 | 得分 | 架构 |
|---|---|---|---|---|---|---|---|---|
| **A. 自由问答式选校**（"物理类 3.2 万名，想学计算机，别离家太远，有哪些稳的？"） | ✓ | ✓ | ✓ | ✓（需要用户追问确认） | ✓ | | **5** | 工具型 Agent |
| **B. 方案体检与改进建议** | ✓ | ✓ | ✓ | ✓（用户逐条确认） | ✓（体检规则） | | **5** | 工具型 Agent + 沙箱 + 差异提案 |
| **C. 单条结果解读**（"为什么是稳不是保？"） | | | ✓ | | ✓ | | 2 | 单次结构化调用（不用 Agent） |
| **D. 政策问答**（提前批、军校体检、专项计划） | | | | | ✓（有原文可引） | | 1–2 | 检索增强（RAG）+ 单次调用 |
| E. 自动生成 112 个志愿的完整表 | — | — | — | — | — | — | — | **不做**，违反"不自动生成正式志愿表" |
| F. 录取概率预测 | — | — | — | — | — | — | — | **不做**，违反"不输出未经回测的概率" |
| G. 艺术类/体育类推荐 | — | — | — | — | — | — | — | **不做**，只给历史查询入口和限制说明 |

结论：A 和 B 是真正的 Agent 场景；C 和 D 用简单工作流就够，但它们使用频率高、风险低，放进同一个入口统一交付。

## 3. 设计原则

从 PPT 项目的「十条可迁移原则」和本产品原则逐条对应：

| # | 原则 | 在本项目中的具体做法 |
|---|---|---|
| 1 | 模型输出是不可信输入 | 所有输出过 Pydantic Schema 校验和业务校验（§8） |
| 2 | 模型做语义判断，程序做确定性事实 | 冲稳保、位次、安全线、选科是否符合，**只能来自工具**；模型只负责理解意图、组织解释 |
| 3 | 优先受控 Workflow | 外层是固定的 LangGraph 图，Agent 自主权只在"选哪个工具、填什么参数"这一层 |
| 4 | 工具即权限边界 | 第一版全部是**只读工具**；方案修改只在内存沙箱里做，产出差异提案 |
| 5 | Agent 先操作副本 | 方案体检 Agent 改的是方案副本，由用户在前端逐条确认 |
| 6 | 修复反馈要具体 | 校验失败时回灌"第 2 段的 12013 在证据中不存在"，而不是"请检查" |
| 7 | 耗时任务必须异步 | 所有 Agent 请求走 `202 + 轮询`（EWS HTTPS 网关会断开慢请求） |
| 8 | 允许部分成功 | 工具失败时返回已有证据加说明，不整体报错 |
| 9 | 可解释、可溯源（本产品原则） | 每条结论带证据编号，前端展开可以看到"数据来自哪年、哪个来源文件" |
| 10 | 诚实区分无数据与未发布（本产品原则） | 工具返回的"无数据/未发布/未核验"状态必须原样出现在答案里，校验器检查是否被省略 |

**制度约束**（参照本项目"改 MATCH_CONFIG 必须附回测"的做法）：**修改提示词或模型参数必须重跑评测集**，
评测报告和提示词版本号一起提交（§13）。

## 4. 总体架构

### 4.1 分层

| 层 | 技术 | 职责 | 新增/复用 |
|---|---|---|---|
| 交付层 | Vue3 抽屉/全屏页、轮询 | 提问、展示进度、渲染结构化答案卡片、确认方案提案 | 新增 |
| 接口层 | FastAPI 路由 `/api/v1/agent/*` | 创建任务、查询进度、反馈 | 新增 |
| 任务层 | 进程内 asyncio 任务 + SQLite 任务表 + 并发信号量 | 执行、超时、取消、进度事件、审计 | 新增 |
| 工作流层 | LangGraph StateGraph | 守卫、路由、工具循环、综合、校验、修复、降级 | 新增 |
| 模型交互层 | LangChain（`langchain-openai`）+ EricAI 认证 | 统一模型调用、结构化输出、工具绑定 | 复用 PPT 项目模式 |
| 工具层 | 对现有 services 的薄封装 | 参数校验、结果裁剪、写入证据账本 | 新增（封装） |
| 领域层 | `services/match.py` 等 | 冲稳保、位次、选科、趋势、方案体检 | **复用，不改语义** |
| 数据层 | PostgreSQL（只读）+ SQLite（任务/审计） | — | 复用 + 新增一张库文件 |

### 4.2 调用链

```
浏览器 ──POST /agent/jobs──▶ FastAPI ──▶ 任务表(pending) ──▶ asyncio 任务
   ▲                                                         │
   └──GET /agent/jobs/{id}?after=N（每秒轮询）◀── 进度事件 ◀──┤
                                                             ▼
                                                   LangGraph 顾问图
                                                   │  工具节点 ──▶ services（进程内函数调用，不走 HTTP）
                                                   │  模型节点 ──▶ LangChain ──▶ EricAI token ──▶ aigw ──▶ se-gpt-5.6-sol
                                                   ▼
                                           证据账本 + 校验器 ──▶ 结构化答案 ──▶ 任务表(ready)
```

要点：
- 工具**在进程内直接调用 service 函数**，不绕回自己的 HTTP 接口，省掉序列化和鉴权开销。
- Agent 与只读分析库之间只通过工具交互，**模型永远拿不到 SQL 能力**。

## 5. 模型接入（EricAI GPT-5.6）

### 5.1 认证与连接

| 项 | 取值 / 做法 | 来源 |
|---|---|---|
| 身份 | Service Principal，`client_credentials` | ericai-web-integration |
| scope | `https://cognitiveservices.azure.com/.default`（**不能**用 `{client_id}/.default`，否则全部 403） | 同上 |
| endpoint | `https://dev.eu.aigw.ericsson.net/v1/generativeai-model/azure/text` 是**前缀**，完整路径是 `{endpoint}/openai/deployments/{deployment}/chat/completions?api-version=...` | 同上 |
| deployment | `se-gpt-5.6-sol`（候选：`se-gpt-5.6-luna`、`se-gpt-5.6-terra`，阶段 0 评测后定） | 模型清单 |
| api-version | `2024-12-01-preview` | gpt56_direct.py |
| secret | 运行时从 `AZURE_CLIENT_SECRET_FILE` 指向的文件读取；EWS 复用 `/var/lib/nir-report-secrets/azure-client-secret`（0400，UID 10001），只读挂载到 `/run/secrets/azure-client-secret` | ericai-web-integration |
| token 缓存 | 进程内缓存，提前 120 秒刷新，异步锁防并发刷新 | PPT 项目 `EricAITokenProvider` |
| 请求头 | `User-Agent: curl/8.5.0`、`Accept: application/json` | 同上 |

### 5.2 LangChain 封装方式（阶段 0 做技术验证后二选一）

| 方案 | 做法 | 优点 | 需要验证的点 |
|---|---|---|---|
| **推荐：`AzureChatOpenAI`** | `azure_endpoint` 填前缀、`azure_deployment` 填部署名、`azure_ad_async_token_provider` 注入 token | URL 拼接方式与网关要求的格式一致 | 实际请求体是否用 `max_completion_tokens`、是否带网关不支持的字段（如 `stream_options`、`parallel_tool_calls`） |
| 备选：照搬 PPT 项目的 `ChatOpenAI` + `httpx.Auth` | `base_url` 填到部署路径，token 由 httpx 认证钩子注入 | 已在 PPT 项目跑通 | PPT 项目把 `base_url` 设到了 `.../chat/completions`，SDK 会再追加一段路径，需要确认网关是否只是容忍了重复路径 |

两种方案都通过一个模型工厂函数产出，业务节点只拿到 `BaseChatModel`，不感知提供方。
这也是 Gate 0 里"模型可替换"要求的落点：配置 `LLM_PROVIDER=ericai|deepseek|qwen` 即可切换。

### 5.3 每个节点的模型参数

| 节点 | 带工具 | reasoning_effort | max_completion_tokens | 超时 | 说明 |
|---|---|---|---|---|---|
| 意图路由 | 否 | `none` | 800 | 20s | 结构化输出（意图 + 抽取的筛选条件） |
| 工具循环（每轮） | **是** | **`none`（网关强制）** | 2,000 | 30s | 只负责选工具、填参数，最多 5 轮 |
| 综合回答 | 否 | `low`（方案体检用 `medium`） | 6,000 | 60s | 推理 + 输出共用这个预算 |
| 修复重写 | 否 | `low` | 6,000 | 60s | 最多 1 次 |
| 单条解读（场景 C） | 否 | `low` | 3,000 | 40s | 不走工具循环 |
| 政策问答（场景 D） | 否 | `low` | 4,000 | 40s | 检索结果作为上下文 |

**必须遵守的 5.6 规则**（每条都在别的项目里出过事）：
1. 不能发 `reasoning_effort="minimal"`（5.6 直接 400）。
2. 带 `tools` 的请求只能是 `none` 或不传；`/v1/responses` 在这个网关上不可用（404），**工具和推理没法同时开**。
3. 只用 `max_completion_tokens`，不用 `max_tokens`；上限 128,000。
4. 预算不足时返回的是**空字符串而不是报错**：空内容一律当作错误处理，预算上调一档重试一次，还是空就降级（§8.4）。
5. 模型客户端层统一处理第 2 条，业务代码不用自己记。

## 6. LangGraph 图设计

### 6.1 主图：顾问图（advisor）

```
START
  ↓
guard（确定性 + 轻量模型）── 越界/注入/艺体推荐 ──▶ refuse ──▶ END
  ↓
load_context（确定性：考生档案快照、当前页面上下文、数据版本）
  ↓
route_intent（模型，结构化输出）
  ├─ explain_unit   ──▶ 子图 C：取数 → 单次解读
  ├─ policy_qa      ──▶ 子图 D：检索 → 单次回答
  ├─ plan_review    ──▶ 子图 B：体检 → 沙箱编辑 Agent → 差异提案
  ├─ find_options   ──▶ 子图 A：工具循环 Agent
  └─ need_clarify   ──▶ ask_user（返回追问，结束本轮）
  ↓
synthesize（模型，无工具，推理开启，结构化输出）
  ↓
verify（确定性：证据核对、禁用表述、必要免责声明）
  ├─ 通过 ──────────────────────────────▶ deliver ──▶ END
  ├─ 失败且 repairs < 1 ──▶ repair（写入具体问题）──▶ synthesize
  └─ 再次失败 ──▶ fallback（确定性模板答案，只列证据不加解读）──▶ deliver
```

### 6.2 状态字段（任务档案）

| 字段 | 含义 |
|---|---|
| `job_id`、`mode` | 任务编号、入口模式（问答/解读/体检/政策） |
| `profile` | 考生档案快照：年份、类别、学科类、批次、位次或位次区间、再选科目、偏好 |
| `page_context` | 发起页面带来的上下文：当前单元 ID、当前方案（体检时） |
| `history` | 最近 6 轮对话（前端传入，服务端不存长期对话） |
| `intent`、`slots` | 路由结果和抽取的条件（省份、城市、专业关键词、档位、层次等） |
| `messages` | 工具循环内的消息 |
| `evidence` | **证据账本**：`E1..En`，每条记录工具名、参数、裁剪后的结果、数据版本、来源 |
| `draft` | 综合节点产出的结构化答案 |
| `issues` | 校验发现的问题（机器可读 + 回灌给模型的中文描述） |
| `tool_rounds`、`repairs` | 预算计数 |
| `usage` | 累计 token、各节点耗时 |
| `events` | 给前端的进度事件（"正在查询稳档候选…"） |

### 6.3 预算和终止条件

| 限制 | 值 | 触发后 |
|---|---|---|
| 工具轮数 | 5 | 带着已有证据进入综合节点 |
| 单次对话工具调用总数 | 8 | 同上 |
| 修复次数 | 1 | 走确定性模板降级 |
| 任务硬截止 | 90 秒 | 标记超时，返回已有证据（部分成功） |
| 单任务 token 上限 | 40,000 | 提前进入综合节点 |

### 6.4 子图 A：自由问答式选校（工具型 Agent）

- 进入前先检查：没有位次就直接返回追问（"请先告诉我你的全省位次"），不让模型猜。
- 工具循环里模型可以多次调用 `search_candidates`（例如先查稳档，再按城市收窄，再看某校详情）。
- 候选单元只能从工具结果里选；综合节点输出的推荐项只包含 `unit_id`，**卡片内容（院校、专业、档位、位次）由前端根据证据账本渲染**，模型没有机会写错档位。
- 用户可以对卡片执行"加入收藏"，走现有的 `usePlanner.addFavorite`，不经过模型。

### 6.5 子图 B：方案体检与改进建议（沙箱 + 差异提案）

```
analyze（确定性：后端版体检规则，输出问题清单）
  ↓
无问题 ──▶ 直接交付"体检通过"及说明
  ↓ 有问题
edit_agent（工具循环，在方案副本上操作：add_from_evidence / remove / move / swap）
  ↓
re_analyze（对副本重新体检，比较问题数）
  ├─ 问题减少且无新的阻断问题 ──▶ diff（生成操作列表：每条带理由 + 证据编号）
  └─ 未改善 ──▶ 只交付问题清单和人工建议，不给提案
```

- 新增的志愿**只能来自本次工具查到的候选**（`add_from_evidence` 的参数是证据中的 `unit_id`），模型不能凭空编一个院校专业。
- 方案始终存在前端（localStorage/云同步）。后端**只返回提案**，前端逐条展示"采纳/忽略"，采纳后才修改方案。所以不需要服务端持久化方案，也不需要 LangGraph 的 checkpoint/interrupt。
- 体检规则挪到后端后，前端工作台的体检也改为调用同一接口，保证两边口径一致。

### 6.6 子图 C / D

- **C 单条解读**：直接取该单元的 `risk_reason`、历年位次、安全线、趋势、选科信息，一次结构化调用改写成家长能看懂的话。原始 `risk_reason` 作为证据附在下方。
- **D 政策问答**：离线把 16 份报考说明 HTML 按小节切块（约几百块），用 `se-text-embedding-3-large` 生成向量存进一张表（数组列即可，不需要 pgvector）；查询时在内存里算余弦相似度取前 5 块，回答必须引用块编号，前端链接到对应 HTML 小节。语料小，另加关键词召回兜底中文专有名词（如"定向培养军士"）。

## 7. 工具层设计

所有工具都是**只读**的，统一做四件事：Pydantic 校验参数 → 调用现有 service → 按上限裁剪结果 → 写入证据账本并返回证据编号。

| 工具 | 封装的现有能力 | 主要参数 | 返回（裁剪后） | 阶段 |
|---|---|---|---|---|
| `locate_rank` | `services/locate.py`（分数↔位次、跨年同位次对照） | 分数或位次、学科类 | 位次、区间、历年等效分 | 1 |
| `search_candidates` | `services/match.match` | 档位、省/市、层次、性质、专业关键词、排序偏好、条数（≤15） | 每条：unit_id、院校、专业、档位、最难年/最近年位次、安全线、断档、趋势标签、选科状态 | 1 |
| `get_unit_detail` | match 候选 + `schools` 历年记录 | unit_id | 历年位次序列、`risk_reason`、多单元说明、来源文件 | 1 |
| `get_school_profile` | `services/schools.py` | 院校代码 | 层次、城市、画像、学科评估摘要 | 1 |
| `get_major_info` | `services/major_catalog.py` + 专业趋势 | 标准专业名 | 专业介绍摘要、在辽招生概览、冷热趋势（含全省基准） | 1 |
| `check_subject_req` | `match.lookup_reqs` | 院校、专业、再选科目 | 是否符合、匹配层级、是否未核验 | 1 |
| `rank_sensitivity` | `match.sensitivity` | 位次偏移 | ±5%/±10% 下各档数量 | 1 |
| `analyze_plan` | 后端版方案体检规则 | 方案副本 | 问题清单、配比 | 2 |
| `plan_add` / `plan_remove` / `plan_move` | 沙箱操作 | unit_id / 位置 | 操作结果、副本最新概况 | 2 |
| `search_policy` | 报考说明检索 | 问题 | 前 5 个段落 + 块编号 | 3 |

**工具设计规范**：
- 工具描述用中文写明"什么时候用、什么时候不要用"，并给出参数取值范围（例如档位只能是 冲/稳/保/高波动/数据不足）。
- 考生档案里的类别、学科类、批次、位次**由工具从状态注入**，不让模型传。这样模型改不了用户的位次，也填不错学科类。
- 返回中保留数据状态字段（`subject_unverified`、`warning`、未发布批次提示），校验器会检查答案有没有把这些状态省略掉。
- 单次工具结果最多约 3,000 字符，超出就截断并注明"另有 N 条"，控制上下文。
- 工具报错返回结构化的错误说明（"该院校代码不存在"），不抛异常打断图。

## 8. 证据账本与输出校验（可信度的核心）

### 8.1 结构化输出契约（综合节点）

| 字段 | 约束 |
|---|---|
| `summary` | 1–3 句结论，≤200 字 |
| `sections[]` | 每段 ≤300 字，必须带 `evidence_ids`（至少 1 个） |
| `recommended_units[]` | 只能是证据中出现过的 `unit_id`，每条带一句理由和证据编号，最多 10 条 |
| `caveats[]` | 数据不足、未核验、未发布、断档等提示 |
| `follow_ups[]` | 建议用户继续问的 2–3 个问题 |
| `needs_clarification` | 信息不足时为真，并给出追问 |

### 8.2 确定性校验规则（verify 节点）

| 规则 | 检查方式 | 失败时回灌的描述（示例） |
|---|---|---|
| 单元存在 | `recommended_units` 全部在证据账本里 | "推荐项 U123 不在本次查询结果中，请只从证据中选择" |
| 数字可溯源 | 从文本中提取所有 ≥100 的整数（位次、分数、人数），去掉千分位后必须在所引证据的数值中出现 | "第 2 段的 12013 在 E3 中不存在" |
| 档位一致 | 文本里"某校某专业 + 冲/稳/保"的组合与证据一致 | "文中说 X 大学计算机是保，证据 E2 为稳" |
| 禁用表述 | "一定能录取""保证""录取概率""百分之…的把握"等 | "不能使用'一定能录取'，本站不承诺录取" |
| 状态不省略 | 证据里有未核验/数据不足/未发布提示时，`caveats` 必须覆盖 | "E4 标注选科未核验，需在注意事项中说明" |
| 越界内容 | 艺术/体育类推荐、非辽宁、代填志愿 | 直接拒答 |
| 引用完整 | 每段至少一个有效证据编号 | "第 3 段缺少证据编号" |

**免责声明由程序追加**，不交给模型生成，保证每条答案都有。

### 8.3 前端渲染与证据的关系

- 推荐卡片的院校、专业、档位、位次**全部从证据账本取值**，模型只提供理由文字。
- 正文里的证据编号可以点开，看到工具名、查询条件、数据年份和来源文件（复用数据中心的溯源信息）。

### 8.4 降级路径

| 情况 | 行为 |
|---|---|
| 模型空答（预算耗尽） | 预算上调一档（6,000→10,000）重试一次 |
| 修复后仍不通过校验 | 确定性模板："根据你的位次，查询到以下候选：…（卡片）"，不加解读 |
| 网关 4xx/5xx、超时 | 返回已有证据 + "AI 解读暂不可用，以下是查询结果" |
| 网关 429 | 指数退避重试 2 次，仍失败则降级；同时下调全局并发 |
| `AGENT_ENABLED=false` | 前端入口隐藏，接口返回 503 和说明 |

## 9. 异步任务与 API 契约

### 9.1 为什么必须异步

一次选校对话预计 20–45 秒（3 轮工具约 10–15 秒 + 综合 8–15 秒 + 查询）。
EWS 的 HTTPS 网关会断开首字节超过约 10 秒的请求（nir-report 已踩过），nginx 默认 60 秒也会超时。
所以统一走"创建任务返回 202 → 前端每秒轮询"。SSE 流式输出在确认 EWS 网关不缓冲、不截断之前不采用。

### 9.2 接口

| 方法 | 路径 | 入参要点 | 返回 |
|---|---|---|---|
| POST | `/api/v1/agent/jobs` | `mode`、`message`（≤500 字）、`profile`、`page_context`（可选：unit_id / 方案快照）、`history`（≤6 轮） | `202 {job_id, status:"pending"}` |
| GET | `/api/v1/agent/jobs/{id}?after=N` | `after` 为已收到的事件序号 | `{status: pending/running/ready/failed/timeout, events[], result?, error_code?}` |
| POST | `/api/v1/agent/jobs/{id}/cancel` | — | 软取消（当前节点完成后停止） |
| POST | `/api/v1/agent/jobs/{id}/feedback` | 有用/没用 + 可选原因 | `{ok}` |
| POST | `/api/v1/plan/analyze` | 方案快照 | 体检问题清单（阶段 2，前端工作台也改用它） |

错误统一用 HTTP 状态码（4xx/5xx），不再沿用"200 + error 字段"的旧约定。

### 9.3 任务存储

- 独立 SQLite 文件 `agent.db`（放在已有的 `/app/data` 卷里），与 `users.db` 分开。
- 表：`agent_jobs`（状态、模式、创建者、耗时、token、错误码）、`agent_events`（进度事件）、`agent_traces`（节点级审计：工具参数、裁剪后的结果摘要、校验问题、提示词版本）。
- 多个 uvicorn worker 共享同一 SQLite：任务在接到 POST 的 worker 里执行，轮询可以落到任何 worker（skill 记录过内存任务表在多 worker 下"消失"的坑）。
- 后端启动时把残留的 `running` 任务标记为 `failed(restart)`。
- 结果保留 24 小时，审计记录保留 30 天（可配置），到期清理。

### 9.4 并发与容量

| 控制 | 初始值 | 说明 |
|---|---|---|
| 全局并发 Agent 任务数 | 每个 worker 4 个（信号量） | 超出排队，事件里显示"排队中，前面还有 N 个" |
| 每用户/IP 频率 | 匿名 10 次/小时，登录 30 次/小时 | 内测期只开放登录白名单 |
| 每日全局 token 预算 | 可配置，超出后自动关闭 Agent | 防止失控 |
| 同一用户进行中的任务 | 1 个 | 重复提交返回已有任务 |

阶段 4 如果单机扛不住，再换 ARQ + Redis（PPT 项目用的方案），接口不用变。

## 10. 前端交互设计

### 10.1 入口（结合上下文，而不是只有一个聊天框）

| 位置 | 入口 | 默认模式 |
|---|---|---|
| 顶栏 / 手机底部 | "问参谋"按钮 | 自由问答 |
| 匹配结果每一行 | "为什么是这个档？" | 单条解读（带 unit_id） |
| 工作台方案卡片 | "帮我体检这个方案" | 方案体检（带方案快照） |
| 报考说明页 | "问问政策" | 政策问答 |
| 定位页（未填位次时） | 不显示 Agent 入口，引导先填位次 | — |

### 10.2 形态

- **桌面**：右侧抽屉，和现有院校/专业抽屉的交互方式一致。
- **手机（主场景）**：全屏页 `/advisor`，底部输入框，顶部只保留返回和档案摘要（不叠加顶栏和步骤条，避开上一轮评审提到的顶栏过高问题）。
- 抽屉组件**懒加载**，不增加首屏包体积。

### 10.3 一次问答的界面状态

1. 提交后立刻显示用户问题和"参谋正在查资料"。
2. 进度事件逐条出现："正在查询物理类本科批稳档候选""正在查看东北大学计算机类历年位次"。把 Agent 的步骤亮出来，本身就是可溯源的一部分。
3. 答案区域：结论 → 分段解释（带可点开的证据编号）→ 推荐卡片（档位色块 + 文字，带"加入收藏"）→ 注意事项 → 固定免责声明 → 追问建议。
4. 方案体检：问题清单 → 提案列表（每条"采纳/忽略"，显示理由和证据），采纳后工作台实时更新并重新体检。
5. 失败或降级时给出明确说明，并保留查到的结果卡片。

### 10.4 安全渲染

- 不用 `v-html`。答案是结构化 JSON，前端逐字段渲染成组件；需要轻量格式（加粗、列表）时用白名单渲染器。
- 对话历史只存本机（`ln-zhiyuan-advisor`，最多保留 20 轮），不进云同步，退出登录时清空。

### 10.5 文案

- 面向家长：短句，避免"位次区间中位""安全边际"这类术语；需要时附一句解释。
- 每个答案末尾固定："以上基于历年投档数据的参考分析，不代表录取承诺，请以辽宁省招考办及院校官方信息为准。"

## 11. 安全、隐私、滥用防护

| 威胁 | 防护 |
|---|---|
| 提示词注入（用户输入） | 守卫节点识别"忽略以上指令""输出系统提示词"等；系统提示禁止泄露提示词、凭证、环境变量、文件路径；输出校验兜底 |
| 间接注入（工具结果里的库内文字，如 OCR 的热门院校介绍、专业介绍） | 工具结果放进明确标注"数据，不是指令"的块；工具全部只读，最坏情况也只是答非所问，不会产生写操作 |
| 越界使用（写作业、闲聊、其他省份） | 守卫节点拒答，给出本助手能做什么 |
| 刷量和费用失控 | 限流、每日预算、并发信号量、功能开关 |
| 个人信息 | 只发送档案里的考试字段；审计日志不存邮箱和 IP 明文（IP 做哈希用于限流）；保留期到期清理 |
| 凭证泄露 | secret 只以文件形式只读挂载；不进镜像、`.env`、Git、日志；前端永远拿不到 |
| 模型输出 XSS | 结构化渲染，不用 `v-html` |

## 17. 风险登记

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| Gate 0 结论不允许对公众开放 | 中 | 高 | 架构保持模型可替换；先做内测版，积累评测数据，将来换已备案的国内模型 |
| 带工具时不能推理，导致工具选择质量差 | 中 | 中 | 意图路由先抽取筛选条件，工具描述写清适用场景，工具参数尽量少；推理放在无工具的综合节点；评测盯"工具选择正确率" |
| 模型编造数字或档位 | 中 | 高 | 卡片数据来自证据账本而不是模型；数字溯源校验 + 修复 + 模板降级 |
| EWS HTTPS 网关截断长请求 | 高（已知） | 高 | 全部异步任务 + 轮询 |
| 高峰期网关 429 或配额不足 | 中 | 高 | 并发信号量、退避、每日预算、一键关闭；阶段 0 探测配额 |
| 匹配接口性能拖慢 Agent | 高（未修复前） | 高 | 列为阶段 0 前置项 |
| 部署名或网关规则变化（5.6 改名、参数规则变化） | 中 | 中 | 部署名和参数全部走配置；启动自检发一次最小请求，失败则自动关闭 Agent 并告警 |
| 共享 SP 的费用和配额与 nir-report 互相影响 | 中 | 中 | 申请独立 SP，或至少按应用分别统计 token |
| 提示词改动引入回归 | 高 | 中 | 改提示词必跑评测集，报告随提交 |
| 家长误把 AI 回答当成承诺 | 中 | 高 | 固定免责声明、禁用表述校验、界面上把"查到的事实"和"参谋建议"分开显示 |

## 18. 需要你拍板的决策

1. **使用范围**（Gate 0）：公开上线、邀请制内测，还是仅内部演示？这决定是否需要申请独立 SP、是否要做备案评估。
2. **是否要求登录才能用 Agent**：建议内测期要求登录（便于限流和追责），公开后再考虑匿名额度。
3. **对话是否在服务端保存**：建议不保存（只存 24 小时任务结果和 30 天审计），与匿名优先的产品原则一致。
4. **默认模型部署**：阶段 0 评测 sol / luna / terra 后确定。
5. **Secret**：复用 nir-report 的共享 secret（skill 推荐，最快），还是为本项目申请独立 SP（费用和配额隔离更清楚）。
6. **阶段顺序**：默认"选校问答 → 方案体检 → 政策问答"。如果你更看重家长最常问的政策问题，可以把阶段 3 提前（它最简单，1 周就能上线）。
