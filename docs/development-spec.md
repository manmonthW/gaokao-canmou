## 1. 文档目的

本文档用于指导辽宁高考志愿辅助网站的产品研发、数据治理、接口设计、前端实现、测试和上线。本文只定义开发方案和边界，不包含具体实现代码。

## 2. 项目现状

### 2.3 关键现实约束

- 2026 年数据仍处于录取周期，不能视为全年完整。
- 2026 普通类专科批尚未完整发布或入库。
- 当前只有 2025、2026 两年，适合区间参考，不适合精确概率预测。
- 当前缺少当年招生计划和选科要求，系统只能给出历史匹配，不能完整判断报考资格。
- 艺术、体育需要专业成绩和综合分规则，必须独立建模。
- 部分院校深层画像字段为空，不得在前台生成未经核验的描述。

## 3. 开发目标和范围

### 3.1 MVP 范围

MVP 面向普通类物理和普通类历史考生，完成：

1. 考生档案录入。
2. 分数、位次和省控线定位。
3. 按位次生成可解释的候选范围。
4. 按学校、专业、城市等条件筛选。
5. 查看院校专业详情和历年趋势。
6. 收藏、比较和管理志愿草案。
7. 展示数据来源、更新时间和完整状态。
8. 提供管理员数据质量和发布状态页面。

### 3.2 MVP 外范围

- 正式志愿填报系统对接。
- 录取概率承诺。
- 自动替用户确定最终志愿顺序。
- 艺术、体育冲稳保模型。
- 就业薪酬预测。
- 用户付费和复杂会员体系。
- AI 自动补全缺失事实。

## 4. 总体架构

### 4.1 逻辑分层

系统分为五层：

1. 数据源层：辽宁官方 Excel、PDF、Markdown 校对文本、教育部院校名单和城市辅助数据。
2. 数据处理层：读取、OCR、元数据识别、结构化解析、标准化、校验和加载。
3. 数据存储层：PostgreSQL 业务库、数据版本和质量报告。
4. 应用服务层：查询、定位、匹配、收藏、比较、志愿方案和管理接口。
5. 用户界面层：移动端优先的响应式 Web 应用和内部管理界面。

### 4.2 推荐技术方向

技术选型应满足团队熟悉度、快速交付和长期维护，建议：

- 数据库：继续使用 PostgreSQL 16。
- 后端：Python Web API，与现有 Python ETL 共享领域模型，但 Web 服务与 ETL 进程分离。
- 前端：支持服务端渲染或静态首屏的现代 TypeScript Web 框架。
- 缓存：MVP 可先使用进程缓存；数据量或访问量上升后再引入 Redis。
- 搜索：MVP 使用 PostgreSQL 索引和模糊查询；专业同义词成熟后再评估独立搜索引擎。
- 后台任务：ETL、校验、位次回填和缓存刷新作为独立任务执行。
- 部署：应用、任务和数据库分离，配置全部通过环境变量注入。

### 4.3 进程边界

- Web API 不直接执行 OCR 或全量 ETL。
- ETL 任务不得阻塞用户请求。
- 网站只读取已发布的数据版本。
- 新数据先进入待审核状态，通过质量检查后再发布。
- 管理操作和用户查询使用不同权限账户。

## 5. 数据模型设计

### 5.1 复用现有表

#### `source_files`

用途：保存文件来源、解析状态和溯源信息。

开发要求：

- 增加官方来源 URL。
- 增加来源发布日期、抓取时间和文件校验值。
- 增加数据版本、审核状态和发布状态。
- 将 `loaded` 与“已审核可发布”区分。

#### `schools`

用途：院校基础维度。

开发要求：

- 保留辽宁招生使用的院校代码。
- 增加稳定的内部院校 ID，避免年度代码变化影响关联。
- 院校名称变更和别名独立维护。

#### `admission_scores`

用途：核心历史录取事实。

开发要求：

- “院校＋专业＋批次＋类别＋学科类＋年份＋志愿阶段”视为一个招生记录。
- 常规志愿和征集志愿必须明确区分。
- 增加标准化专业 ID，同时保留原始专业名称。
- 增加招生单元或专业组字段，为后续规则变化预留空间。
- 增加记录质量等级和异常原因。
- 保留原始行和源文件关联。

#### `score_rank`

用途：分数与省位次换算。

开发要求：

- 明确 `cumulative_rank` 表示不低于该分数的累计人数。
- 顶部分数桶在界面中显示为“某分及以上”。
- 分数无法精确映射时返回区间及说明，不能伪造精确名次。

#### `batch_control_line`

用途：省控线判断。

开发要求：

- 普通、艺术、体育分别维护。
- 区分文化控制线和专业控制线。
- 增加规则来源和生效年份。

#### `cities` 与 `school_profiles`

用途：筛选和辅助比较。

开发要求：

- 每个字段记录来源类型和更新时间。
- 规则推导字段与官方字段分开。
- 空字段不展示，不自动生成事实。

### 5.2 建议新增的数据实体

以下是概念设计，字段在实施前需要形成正式数据库迁移评审。

#### 5.2.1 数据发布版本 `data_releases`

用途：让网站只读取经过审核的稳定版本。

建议属性：

- 版本号。
- 数据截止时间。
- 覆盖年份。
- 覆盖类别和批次。
- 状态：草稿、校验中、已发布、已回滚。
- 发布人和发布时间。
- 质量摘要。

#### 5.2.2 批次发布状态 `admission_publication_status`

用途：区分“没有数据”和“尚未发布”。

建议属性：

- 年份、类别、学科类、批次、志愿阶段。
- 状态：待发布、部分发布、已完成、已关闭。
- 官方发布时间。
- 本系统更新时间。
- 来源链接和备注。

#### 5.2.3 标准专业 `majors`

用途：处理专业名称变化、方向后缀和同义词。

建议属性：

- 内部专业 ID。
- 标准专业代码。
- 标准名称。
- 专业类和学科门类。
- 本科或专科层次。
- 别名和关键词。

#### 5.2.4 招生计划 `enrollment_plans`

用途：支持真正的报考资格判断和计划变化分析。

建议属性：

- 年份、院校、专业、招生单元。
- 类别、学科类、批次。
- 计划人数。
- 学制、学费、校区。
- 选科要求。
- 外语、单科、体检和其他限制。
- 来源、版本和质量等级。

#### 5.2.5 用户档案 `candidate_profiles`

用途：保存考生条件。

建议属性：

- 用户或匿名会话标识。
- 高考年份、类别、学科类。
- 分数、位次。
- 地域、院校性质、专业方向偏好。
- 中外合作、高收费、异地校区接受度。
- 创建和更新时间。

隐私原则：只保存完成推荐所需的最少数据，不收集身份证号、准考证号等敏感身份信息。

#### 5.2.6 收藏与方案

建议实体：

- 收藏项。
- 比较清单。
- 志愿方案。
- 方案条目。

方案条目应保存创建时的数据版本和风险快照，防止后续数据更新后用户无法理解结果变化。

#### 5.2.7 数据质量问题 `data_quality_issues`

用途：记录自动校验和人工审核发现的问题。

建议属性：

- 数据版本和源文件。
- 问题类型、严重程度。
- 影响记录数。
- 示例记录。
- 状态、负责人和处理说明。

## 6. 数据治理和发布流程

### 6.1 数据生命周期

1. 获取官方文件。
2. 保存原始文件和校验值。
3. 解析为结构化记录。
4. 执行字段标准化。
5. 运行自动质量检查。
6. 生成人工审核摘要。
7. 审核通过后生成数据版本。
8. 发布版本并刷新查询缓存。
9. 保留上一稳定版本，支持回滚。

### 6.2 必须执行的质量检查

- 源文件数和处理文件数一致。
- 每个文件解析行数与数据库行数一致。
- 最低分和同分排序字段与校对文本一致。
- 年份、类别、学科类、批次不为空或有明确异常标记。
- 院校代码和名称关联合理。
- 最低位次回填率达到发布阈值。
- 常规和征集记录不混淆。
- 同一业务键没有异常重复。
- 分数和位次满足基本单调性。
- 省控线来源和年份完整。
- 当前年度未发布批次有明确状态。

### 6.3 建议发布阈值

普通类默认推荐数据：

- 最低分非空。
- 最低位次非空。
- 类别、学科类、批次完整。
- 来源文件可追溯。
- 质量等级不低于“可用”。

不满足条件的记录仍可在数据中心查询，但默认不进入智能匹配。

### 6.4 数据回滚

- 每次发布都记录独立版本。
- Web 查询绑定当前发布版本。
- 新版本出现严重问题时可切回上一版本。
- 用户志愿方案保留创建时版本号。

## 7. 匹配与风险模型设计

### 7.1 模型输入

必要输入：

- 考生年份。
- 类别。
- 学科类。
- 省位次。
- 目标批次。

可选偏好：

- 地区和城市。
- 院校层次、性质和类型。
- 专业方向。
- 中外合作、高收费和异地校区接受度。
- 风险偏好。

### 7.2 处理步骤

#### 第一步：输入校验

- 位次必须为正整数。
- 分数必须在合理区间。
- 分数与位次同时提供时，提示是否与当前一分一段表明显冲突。
- 当前年份没有一分一段数据时，要求用户直接提供官方位次。

#### 第二步：资格和数据过滤

- 年份选择参考范围。
- 类别和学科类严格一致。
- 批次一致。
- 常规志愿与征集志愿分开。
- 默认排除最低位次为空的数据。
- 后续增加招生计划后，再过滤选科、体检、外语和单科限制。

#### 第三步：构造招生候选单元

候选键至少包含：

- 院校。
- 标准专业或原始专业。
- 批次。
- 志愿阶段。
- 招生单元。

不能只按学校聚合，否则会掩盖同校不同专业之间的大幅位次差异。

#### 第四步：历史统计

每个候选计算：

- 覆盖年份数。
- 最近一年最低分和最低位次。
- 历史最好位次和最差位次。
- 中位位次。
- 位次跨度和相对波动。
- 是否连续招生。
- 是否存在异常断档。
- 招生计划变化；待计划数据接入后启用。

#### 第五步：风险分类

风险分类必须可配置并通过历史回测确定阈值。首版输出：

- 冲。
- 稳。
- 保。
- 高波动。
- 数据不足。

建议先使用规则模型，不使用黑盒模型。分类时同时考虑：

- 考生位次与最近一年最低位次的差。
- 考生是否达到历史更严格年份的位次。
- 历史波动大小。
- 覆盖年份数。
- 是否征集或出现异常断档。

#### 第六步：偏好排序

风险分类完成后，再根据用户偏好排序。偏好不能改变资格判断和基础风险，只能改变同一风险档内的展示顺序。

### 7.3 解释输出

每个结果必须返回可读解释所需的数据：

- 本人位次。
- 参考年份。
- 各年最低位次。
- 最严格年份和最宽松年份。
- 位次差。
- 波动等级。
- 数据覆盖数。
- 风险标签原因。
- 数据不足或特殊情况警告。

### 7.4 回测

在每次调整模型阈值前执行滚动回测：

- 用较早年份预测较新年份。
- 分位次区间分别统计。
- 按物理、历史分开统计。
- 按本科、专科和提前批分开统计。
- 统计每个风险档在下一年的实际覆盖情况。
- 重点检查断档、中外合作、小语种、定向和征集等异常样本。

只有回测稳定后才允许显示概率；MVP 不显示概率。

## 8. 应用服务接口规划

接口使用版本化路径。以下为业务契约，不限定具体框架。

### 8.1 公共元数据

| 能力 | 输入 | 输出 |
|---|---|---|
| 获取数据状态 | 无或年份 | 当前版本、截止时间、已完成和待发布批次 |
| 获取筛选选项 | 类别、学科类 | 年份、批次、地区、院校类型等枚举 |
| 获取免责声明 | 场景 | 对应风险提示和官方说明 |

### 8.2 定位服务

| 能力 | 输入 | 输出 |
|---|---|---|
| 分数转位次 | 年份、类别、学科类、分数 | 位次或位次区间、同分人数、来源 |
| 位次转分数 | 年份、类别、学科类、位次 | 对应分数或分数区间 |
| 省控线判断 | 年份、类别、学科类、批次、分数 | 控制线、分差、是否过线、说明 |
| 个人定位摘要 | 考生档案 | 百分位、过线情况、跨年同位次分数 |

### 8.3 匹配服务

输入：

- 考生基本信息。
- 参考年份。
- 筛选条件。
- 风险偏好。
- 分页和排序。

输出：

- 当前数据版本。
- 候选总数和各风险档数量。
- 候选列表。
- 每项历史数据、位次差、波动和解释。
- 数据缺失和限制提示。
- 可用筛选聚合结果。

### 8.4 搜索和详情

| 能力 | 说明 |
|---|---|
| 搜索院校 | 支持名称、简称和别名 |
| 搜索专业 | 支持原始名称、标准名称和关键词 |
| 院校详情 | 画像、城市、历年招生专业、数据来源 |
| 院校专业详情 | 历年最低分、最低位次、批次和趋势 |
| 城市详情 | 基础画像及在该城市招生院校 |

### 8.5 用户方案

| 能力 | 说明 |
|---|---|
| 保存档案 | 匿名本地或登录用户档案 |
| 收藏候选 | 保存候选及数据版本 |
| 创建方案 | 设置方案名和说明 |
| 添加方案条目 | 保存顺序、风险快照和备注 |
| 调整顺序 | 支持批量排序 |
| 方案分析 | 风险结构、数据缺失、重复和集中度提醒 |
| 导出方案 | 生成可打印文件或结构化文件 |

### 8.6 管理接口

- 上传或登记源文件。
- 查看 ETL 运行记录。
- 查看质量问题。
- 审核数据版本。
- 发布或回滚版本。
- 更新批次发布状态。
- 管理专业映射和院校别名。

管理接口必须独立鉴权并记录审计日志。

## 9. 前端设计

### 9.1 路由规划

| 页面 | 目的 |
|---|---|
| 首页 | 输入考生信息和展示定位摘要 |
| 智能匹配 | 查看和筛选冲稳保结果 |
| 院校搜索 | 搜索和浏览院校 |
| 专业搜索 | 搜索和浏览专业 |
| 院校详情 | 查看院校画像和在辽录取历史 |
| 院校专业详情 | 查看具体招生单元历年趋势 |
| 对比中心 | 对比三至五个候选项 |
| 我的方案 | 收藏和志愿草案管理 |
| 数据中心 | 省控线、一分一段、来源和更新状态 |
| 使用说明 | 口径、算法解释和免责声明 |
| 管理后台 | 数据质量、发布和回滚 |

### 9.2 主要页面组件

#### 考生条件栏

- 始终显示当前年份、类别、学科类、分数和位次。
- 允许快速编辑。
- 修改关键条件后提示结果将重新计算。

#### 定位摘要卡

- 当前位次。
- 省控线及分差。
- 特控线状态。
- 同位次历年分数。
- 数据更新时间。

#### 候选结果卡

- 学校、专业、城市和标签。
- 风险标签。
- 最近一年最低位次。
- 历年范围。
- 位次差和波动。
- 数据覆盖和来源。
- 收藏、比较和加入方案。

#### 筛选器

移动端采用底部弹层，桌面端采用侧栏。已启用条件以标签展示并可单独清除。

#### 趋势图

- 位次为默认主轴。
- 明确“位次数值越小，排名越靠前”。
- 分数趋势作为切换视图。
- 缺失年份不连线，避免误导。

#### 数据状态横幅

当前年度批次不完整时，在首页、匹配页和详情页统一展示，不允许只隐藏在说明页。

### 9.3 状态管理

前端状态分为：

- 考生档案状态。
- 当前筛选和排序状态。
- 服务端查询结果。
- 收藏和对比状态。
- 志愿方案状态。
- 当前数据版本。

MVP 匿名用户数据可本地保存；注册后需提供明确的合并策略。

### 9.4 空状态和错误状态

必须区分：

- 条件下确实没有历史记录。
- 当前批次尚未发布。
- 数据正在更新。
- 记录存在但不满足质量要求。
- 网络或服务故障。
- 筛选条件过严。

每种状态给出不同解释和下一步操作，不能统一显示“暂无数据”。

### 9.5 响应式和可访问性

- 移动端优先。
- 风险标签同时使用颜色、文字和图标。
- 图表提供文字摘要。
- 表格在小屏幕下切换卡片模式。
- 键盘可操作。
- 表单具备明确标签和错误提示。
- 颜色对比满足基本可访问性要求。

## 10. 管理后台

### 10.1 仪表盘

展示：

- 当前发布版本。
- 各年份、类别、学科类和批次覆盖情况。
- 最近 ETL 任务。
- 位次回填率。
- 解析失败文件。
- 数据质量问题。
- 当前年度待发布批次。

### 10.2 数据审核

审核人员可以：

- 查看源文件元数据。
- 比较源文件解析数和数据库记录数。
- 查看差异样例。
- 标记异常记录。
- 批准或拒绝数据版本。

### 10.3 字典维护

- 院校别名。
- 专业标准名称和别名。
- 批次标准名称。
- 城市名称归一化。
- 中外合作、定向、专项等标签规则。

所有修改保留操作人、时间和前后值。

## 11. 安全与隐私

### 11.1 配置安全

- 数据库连接信息不得硬编码在生产代码中。
- 密码、密钥和连接串仅通过环境变量或密钥管理系统注入。
- 开发、测试和生产环境使用不同账户。
- Web 服务数据库账户默认只读，用户方案写入使用最小权限。

现有配置中存在本地默认数据库口令，进入正式开发前应移除并轮换相关凭据。

### 11.2 用户隐私

- 不收集身份证号、准考证号。
- 分数、位次和偏好按个人教育信息保护。
- 匿名模式默认本地保存。
- 登录用户可删除档案和方案。
- 分析日志不得记录完整个人档案。
- 导出和分享默认不包含用户真实姓名。

### 11.3 接口安全

- 参数校验和查询白名单。
- 分页和最大结果数限制。
- 速率限制。
- 管理接口强鉴权。
- 审计日志。
- 防止批量抓取造成服务不可用。
- 所有生产流量使用 HTTPS。

## 12. 性能设计

### 12.1 查询目标

建议目标：

- 定位查询：95% 请求在 500 毫秒内完成。
- 匹配首屏：95% 请求在 1.5 秒内完成。
- 搜索建议：95% 请求在 300 毫秒内完成。
- 详情页核心数据：95% 请求在 800 毫秒内完成。

### 12.2 数据库优化方向

- 为常用过滤组合建立复合索引。
- 预计算院校专业跨年统计。
- 发布版本完成后生成匹配用物化结果。
- 搜索字段维护归一化文本。
- 所有列表使用服务端分页。
- 避免在用户请求中重复计算全量历史聚合。

### 12.3 缓存

优先缓存：

- 数据状态和筛选枚举。
- 省控线。
- 一分一段映射。
- 院校基础画像。
- 已发布版本的院校专业历史统计。

发布新数据版本时统一失效相关缓存。

## 13. 测试策略

### 13.1 数据测试

- 源文件解析回归测试。
- 文件行数一致性。
- 业务键唯一性。
- 分数位次单调性。
- 位次回填准确性抽样。
- 省控线与官方来源比对。
- 常规和征集隔离。
- 年份和批次发布状态完整性。

### 13.2 后端单元测试

覆盖：

- 分数转位次边界。
- 顶部分数桶。
- 省控线临界分数。
- 位次差计算。
- 风险分类边界。
- 数据不足和异常波动。
- 当前年份无一分一段表。
- 普通、艺术、体育隔离。

### 13.3 接口测试

- 合法和非法输入。
- 分页、排序和筛选组合。
- 空结果类型区分。
- 数据版本一致性。
- 管理权限。
- 并发访问和速率限制。

### 13.4 前端测试

- 考生档案表单。
- 条件修改后结果刷新。
- 筛选器。
- 收藏、比较和方案排序。
- 数据状态横幅。
- 移动端主流程。
- 图表缺失数据表现。
- 网络失败恢复。

### 13.5 端到端场景

至少覆盖：

1. 普通类物理本科考生从定位到生成方案。
2. 普通类历史考生修改位次后重新匹配。
3. 当前年度专科批尚未发布时得到正确提示。
4. 用户查看某院校专业两年趋势并加入比较。
5. 用户创建两套不同偏好的方案。
6. 艺术类用户不会得到普通类冲稳保结果。
7. 数据版本更新后旧方案仍显示原版本说明。

### 13.6 历史回测

模型每次调整必须记录：

- 回测数据版本。
- 训练和验证年份。
- 阈值配置。
- 各位次段和批次表现。
- 异常样本。
- 是否通过发布标准。

## 14. 可观测性和运维

### 14.1 日志

- 请求日志不记录敏感完整档案。
- 匹配请求记录匿名统计维度和模型版本。
- ETL 记录文件、阶段、耗时、行数和错误摘要。
- 管理操作记录审计日志。

### 14.2 指标

系统指标：

- 请求量、延迟、错误率。
- 数据库连接和慢查询。
- 缓存命中率。
- ETL 成功率和耗时。

业务指标：

- 完成定位人数。
- 获得有效候选结果比例。
- 收藏、比较和创建方案比例。
- 无结果原因分布。
- 各筛选项使用率。
- 数据来源查看率。

数据质量指标：

- 最低分完整率。
- 最低位次完整率。
- 院校画像关联率。
- 各批次发布完成率。
- 异常记录数。

### 14.3 告警

- ETL 失败。
- 数据量较上次异常下降。
- 位次回填率低于阈值。
- 发布后接口错误率突增。
- 数据库空间、连接或延迟异常。
- 当前年度官方批次已发布但系统长时间未更新。

## 15. 部署与环境

### 15.1 环境划分

- 本地开发环境。
- 集成测试环境。
- 预发布环境。
- 生产环境。

各环境拥有独立数据库或独立 schema，禁止生产数据发布操作从开发环境直接执行。

### 15.2 发布顺序

1. 执行数据库迁移。
2. 部署后端服务。
3. 执行健康检查。
4. 部署前端资源。
5. 运行核心冒烟测试。
6. 切换流量。
7. 观察错误率和延迟。

数据发布与应用发布相互独立。新数据应先在预发布环境验证，再由管理后台发布。

### 15.3 备份和恢复

- 数据库定期全量备份和增量备份。
- 原始源文件永久保留。
- 数据版本和专业映射纳入备份。
- 定期执行恢复演练。
- 应用支持切换到上一数据版本。

## 16. 开发阶段与交付物

### 阶段 0：数据可信化

交付物：

- 数据发布版本设计。
- 批次发布状态。
- 质量检查报告。
- 常规与征集隔离验证。
- 配置安全整改。
- 当前数据覆盖说明。

完成标准：网站能可靠区分“无数据”和“尚未发布”。

### 阶段 1：只读查询基础

交付物：

- 数据状态服务。
- 省控线和分数位次服务。
- 院校、专业搜索。
- 院校专业详情。
- 数据中心。

完成标准：用户可以查询全部已发布历史数据并看到来源。

### 阶段 2：普通类智能匹配 MVP

交付物：

- 考生档案。
- 匹配服务。
- 冲稳保结果页。
- 筛选、排序和解释。
- 风险模型回测报告。

完成标准：每个匹配结果均有可验证的计算依据。

### 阶段 3：决策工作台

交付物：

- 收藏。
- 对比中心。
- 多志愿方案。
- 梯度分析。
- 导出和分享。

完成标准：用户可独立完成从候选发现到方案整理的完整流程。

### 阶段 4：数据增强

交付物：

- 2023、2024 历史录取数据。
- 招生计划。
- 选科和报考限制。
- 学费、学制和校区。
- 专业标准库。

完成标准：系统可从“历史匹配”升级为“资格过滤＋历史匹配”。

### 阶段 5：艺术体育与智能解释

交付物：

- 艺术类独立规则。
- 体育类独立规则。
- AI 数据解释助手。

完成标准：所有结论均来自结构化数据和公开规则，AI 只负责解释，不生成事实。

## 17. MVP Definition of Done

MVP 被视为完成，必须同时满足：

### 数据

- 当前发布版本明确。
- 每条默认推荐记录可溯源。
- 位次完整率达到既定发布阈值。
- 常规和征集不混用。
- 当前年度未发布批次有明确状态。

### 功能

- 完成定位、匹配、筛选、详情、收藏、比较和方案主流程。
- 支持普通类物理和历史。
- 艺术和体育得到正确限制提示。
- 用户可修改条件并重新计算。

### 解释

- 每个风险标签可解释。
- 显示参考年份、最低位次、位次差和波动。
- 不展示未经验证的精确概率。

### 质量

- 核心自动测试通过。
- 移动端主流程通过。
- 性能达到目标。
- 无高严重度安全问题。
- 数据、应用和数据库均可回滚。

## 18. 待确认决策

开发启动前需要产品负责人确认：

1. 产品首发是否只面向辽宁考生。
2. MVP 是否只开放普通类智能匹配。
3. 用户系统首版采用匿名本地保存还是立即登录。
4. 是否允许用户导出和公开分享方案。
5. 风险标签是否采用“冲稳保＋高波动＋数据不足”。
6. 2023、2024 数据补充是否与前端 MVP 并行进行。
7. 招生计划和选科要求的数据来源及授权方式。
8. 网站公开发布还是仅内部试用。
9. 管理后台的审核和发布负责人。
10. 数据更新时效目标，例如官方发布后多久完成入库。

## 19. 推荐的实施原则

- 先保证数据可信，再优化推荐算法。
- 先做普通类完整闭环，再扩展艺术和体育。
- 先使用可解释规则模型，再考虑机器学习。
- 先补招生计划和选科要求，再宣传“可报”。
- 每个页面都显示数据时间和适用范围。
- 所有缺失和不确定性都应显式表达，不能用默认值掩盖。
- AI 可以解释结果，但不能代替数据、规则和人工审核。
